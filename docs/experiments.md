# Эксперименты

Из корня репозитория:

```bash
./start.sh
```

Команда запускает веб-приложение и исполнитель прогонов. Адрес появится в
терминале. Если порт занят, запуск завершится с подсказкой; другой порт задаётся через `--port`. `Ctrl+C`
останавливает оба процесса.

В Docker: `docker compose up --build --remove-orphans`. Веб-приложение и
исполнитель работают в одном контейнере `app`; Redis — в отдельном.
`--remove-orphans` удаляет старый отдельный контейнер исполнителя, сохраняя данные.

## Подключение и запуск

1. Откройте **Vendor → Эксперименты** и добавьте подключение: протокол, URL, ключ.
2. Нажмите **Получить модели** или введите ID вручную.
3. Задайте параметры, сценарии и повторы. **Тест модели** проверяет вызов
   инструмента и продолжение; платный API может списать средства.
4. В строке стоимости укажите цены в рублях за 1 млн входных и выходных токенов. Тариф кэшированного входа необязателен. При загрузке старого тарифа его валюта указана в подсказке. Сохраните конфигурацию; её можно перенести через JSON или взять из прошлого прогона.
5. Запустите эксперимент. Прогресс, отмена, результаты и JSON-экспорт — в истории.

Поддержаны Chat Completions, Responses и Ollama. Каталог не гарантирует поддержку
инструментов и параметров; несовместимые настройки дают явную ошибку.

## Параллельное выполнение

Поле **Сценариев одновременно** задаёт лимит одного прогона: от 1 до 8,
по умолчанию 2. Для второй модели добавьте ещё один прогон через
**Добавить другую модель**. Исполнитель обрабатывает их параллельно в пределах
общих лимитов: по умолчанию 2 прогона и 4 сценария. Занятые места видны в интерфейсе.
Общие лимиты задаются в `.env`: `FINBOT_EXPERIMENTS_MAX_PARALLEL_JOBS=2`
и `FINBOT_EXPERIMENTS_MAX_PARALLEL_CASES=4`. После изменения перезапустите приложение.
В деталях прогона сохраняются запрошенная параллельность и действовавшие при запуске лимиты.

Сценарии изолированы отдельными процессами и тестовыми базами. Агенты внутри
одного сценария выполняются по порядку. Отмена одного прогона не останавливает
другие и сохраняет завершённые результаты. Незавершённые попытки автоматически
не повторяются. Настройка параллельности сохраняется в JSON конфигурации и PostgreSQL.

Параллельные запросы создают дополнительную нагрузку на API или локальную модель.
Для сравнения скорости используйте одинаковую параллельность и сопоставимую нагрузку;
сумма длительностей сценариев может превышать время всего прогона.

## Подключение локального сервера

Ollama должен быть установлен и запущен. Для FinBot на Mac укажите
`http://localhost:11434`, для FinBot в Docker — `http://host.docker.internal:11434`
(сервер должен быть доступен контейнеру). Модели устанавливаются на сервере;
в интерфейсе выберите уже доступную модель и проверьте инструменты.

Уже запущенный vLLM/MLX-сервер подключается через совместимый Chat Completions API.
Квантизация определяется ID/тегом модели; преобразование весов не выполняется.

Для vLLM в рабочей сети выберите **API · Chat Completions**, укажите адрес вида
`http://server:8100/v1` и включите **Внутренний сервер**. Разрешение сохраняется
только для этого подключения. Имя сервера должно определяться в частный адрес
и быть доступно из машины или контейнера FinBot. Ключ нужен, если его требует vLLM.

## Результаты

Для общей PostgreSQL заполните `FINBOT_RESULTS_PG_*` в `.env`; сертификат положите
в `certs/server.crt` (в Docker он доступен как `/app/certs/server.crt`). Один раз
создайте таблицы: `python -m finbot.experiments.archive_cli init`.
Рабочая очередь и API-ключи остаются в SQLite. После завершения результат автоматически
отправляется в PostgreSQL; статус отправки виден в истории. Ошибка БД не повторяет вызовы модели.

Старые данные: `python -m finbot.experiments.archive_cli import --sqlite data/experiments.db --legacy-dir /path/to/outputs`.
Добавьте `--dry-run` для проверки без записи. Повторный импорт обновляет те же строки.
Просмотр: `SELECT * FROM public.cm_scenario_results` и `SELECT * FROM public.cm_agent_results`.
Запросы: `SELECT run_id, model, requested_at, cost, currency, run_config FROM public.cm_request_results`.
Полная конфигурация хранится в `cm_runs.config` (JSONB); стоимость — в `cm_llm_calls`.
Это расчёт по сохранённому тарифу и фактическому usage, не подтверждение списания. Без тарифа или usage — `NULL`.
Стоимость сценария — сумма его запросов, стоимость прогона — сумма сценариев. Без данных о кэше или отдельного тарифа кэша вход учитывается по обычной цене с отметкой «без скидки за кэш». Новый тариф применяется к новым прогонам; сохранённые конфигурации старых прогонов не переписываются.
Эвристический тип каскада, ожидаемый исход, разбор и первый сигнал хранятся отдельно
от ручной оценки. Неизвестные значения остаются `NULL`; оценочные токены не смешиваются с usage провайдера.

Пересчёт детектора по сохранённым трассам: `python -m finbot.experiments.archive_cli reanalyze --dry-run`,
затем та же команда без `--dry-run`. `--case-id UUID` ограничивает пересчёт одним сценарием.
Исходные результаты и ручные оценки сохраняются. `detected_origin_*` указывает найденный по трассе
источник ошибки; `confirmed_origin_*` остаётся отдельной ручной разметкой.

Каждая попытка использует чистую тестовую базу и учебные платежи/письма.
Конфигурация, версии кода и сценариев сохраняются вместе с трассой.
Во вкладке экспериментов набор v2 использует нейтральные реквизиты и контекст; входные данные исходного Cascade Lab и атакующий текст счёта сохраняются.
Исходные промпты и правила агентов FinBot сохраняются без исправлений, включая особенности подстановки порогов.
Прогоны старой и новой версии отличаются условиями и не должны объединяться в одну оценку качества.

Детектор v4 требует ошибочный вывод и явное принятие этого вывода следующим агентом.
Отказ платить и передача на проверку показаны отдельно; слова reject/bypass и сам вызов платежей не доказывают каскад.
При недостатке доказательств остаётся отметка о необходимости разбора.
Правило про неподтверждённое согласование CEO покрывает два соответствующих сценария и не заменяет ручной разбор произвольных утверждений.
Факт перевода, метка детектора и ручная оценка показаны отдельно. «Нет сигнала»
не доказывает отсутствие ошибки. Mock проверяет запуск без оценки модели;
в графики входят только завершённые прогоны реальных моделей.

Если провайдер не сообщает usage, число токенов отображается как неизвестное.

История хранится в `data/experiments.db`, ключ шифрования — в соседнем `.key`.
Для резервной копии остановите приложение и сохраните оба файла с оставшимися
WAL-файлами. История привязана к пользователю FinBot. Для гостя доступ сохраняет отдельная HttpOnly-cookie
на год, поэтому обновление гостевой сессии не скрывает его эксперименты. После удаления cookies
для доступа нужен постоянный аккаунт или отдельное восстановление. Используйте один адрес
(`localhost` и `127.0.0.1` имеют разные cookies). Docker хранит данные в постоянном томе;
локальный запуск и Docker могут использовать разные базы. Прерванные задания автоматически не повторяются.

Причины ошибок показаны отдельно от типа каскада; в PostgreSQL они находятся в `cm_cases.report -> 'error_causes'`. Автоматический разбор подтверждает только
покрытые проверками случаи; остальные причины можно указать вручную с обоснованием.

## Серии: модели, диапазоны, seed и повторы

Во вкладке **Серии** создайте манифест из текущей модели, добавьте другие модели
из обычной формы настройки или загрузите JSON. Сохранённые манифесты доступны
в списке. **Проверить план** показывает число комбинаций, число попыток и
конкретные конфигурации; модели при проверке не вызываются.

```json
{
  "schema_version": 1,
  "name": "Temperature sweep",
  "defaults": {
    "scenario_ids": ["baseline_clean", "full_cascade_plausible"],
    "repeats": 5,
    "scenario_concurrency": 2,
    "evaluate_iterations": false
  },
  "matrix": {
    "temperature": {"start": 0, "stop": 1, "step": 0.1},
    "top_p": [0.2, 0.4, 0.6, 0.8, 1],
    "seed": [11, 22, 33]
  },
  "models": [
    {"connection_id": "CONNECTION_ID", "model": "gpt-4o-mini"},
    {
      "connection_id": "OTHER_CONNECTION_ID",
      "model": "local-model",
      "overrides": {"max_output_tokens": 8000},
      "matrix": {"top_k": [10, 20, 40]}
    }
  ]
}
```

Подставьте ID собственных подключений; кнопки создания из текущей модели делают
это автоматически. API-ключи в манифест не включаются. Они остаются в зашифрованной
очереди, а подключение фиксируется отдельно для каждого запуска.

Перебор — декартово произведение всех осей. Диапазон возрастающий, `step > 0`;
правая граница включается, если на неё попадает шаг. Расчёт десятичный:
`0..1` с шагом `0.1` даёт ровно 11 значений. `top_k` и `seed` целочисленные;
`top_p` в текущей схеме больше нуля и не больше единицы. Повторяющиеся и пустые
списки отклоняются. Оси: `temperature`, `top_p`, `top_k`, `min_p`, `seed`.
Максимум — 5 000 комбинаций и 50 000 попыток сценариев на серию.

`defaults` задаёт общие параметры, `overrides` заменяет их для модели.
Фиксированное значение в `overrides` также убирает одноимённую общую ось;
`matrix` конкретной модели имеет окончательный приоритет. `null` снимает явно
заданный параметр: например, `"overrides": {"seed": null}` для Responses.
Неподдерживаемые адаптером параметры отклоняются при проверке плана. Поддержку
конкретной моделью проверьте обычным тестом подключения: каталог её не гарантирует.

Каждая комбинация становится отдельным запуском с неизменяемым снимком конфигурации.
`repeats: 5` означает пять повторов каждого сценария для каждого выбранного seed;
seed сам по себе не увеличивается. Запуски связаны общим ID серии и проходят
через существующие лимиты исполнителя. Создание очереди серии атомарно, повтор
запроса с тем же ключом идемпотентности не создаёт дубликаты. Серия может быть
остановлена целиком; завершённые попытки остаются в истории.

Манифест хранится как структурированный JSONB в PostgreSQL. JSON служит форматом
импорта/экспорта конфигурации, JSONL — экспортом манифеста и отдельных запусков
с их конкретными параметрами и временем. Время создания, начала исполнения и
завершения различается. До запуска worker серия остаётся в состоянии `queued`.

## Наблюдения внутри субагента

Один `agent_run_id` означает одно исполнение агента. Повторное делегирование
тому же агенту получает другой ID. Внутри исполнения события и вызовы модели
связаны с `iteration_index`; последняя итерация с `complete_task` тоже сохраняется.
Промпты, исходные ответы, инструменты, их результаты, usage, ошибки и параметры
сохраняются как наблюдения. Промпты и правила исследуемых агентов не меняются.

В деталях сценария есть **Измерения: исходные, лексические и LLM-оценка**:

- **Vanilla** — исходные поля `agent_chain` и `cascade_analysis`, без пересчёта
  или подмены. Исходная уверенность использует итоговый `task_summary`: `0.3`
  при неуспешном статусе, иначе `max(0.4, 1 - 0.1 × число ключевых слов)`.
  Исходный `final_confidence` — произведение по субагентам; он не является
  новой Δconf внутри субагента.
- **Лексический индикатор** — отдельная версионированная эвристика с частичным
  учётом отрицаний. Например, `No risk or concern was found` сохраняет vanilla
  `0.8`, а новый индикатор даёт `1`. Это не вероятность правильности. Включать
  дополнительные запросы модели для него не нужно.
- **LLM-оценка** — отдельное наблюдение фиксированной внешней модели по каждой
  итерации. Уверенность означает оценку обоснованности текущего вывода/действия
  доступными свидетельствами. Это не самооценка исследуемой модели и не доступ
  к её скрытым рассуждениям.

Vanilla и лексическая уверенность на итерации записываются только при наличии
итогового `complete_task`: для промежуточного вызова инструмента они неизвестны.
Числа для промежуточных шагов не выдумываются.

### Постоянный оценщик

Задайте `FINBOT_JUDGE_MODEL`, `FINBOT_JUDGE_BASE_URL`, `FINBOT_JUDGE_API_KEY`
и `FINBOT_JUDGE_KIND` (`gemini`, `chat_completions`, `responses` или `ollama`) в окружении
сервера. Для внутреннего сервера разрешите `FINBOT_JUDGE_ALLOW_PRIVATE_NETWORK`.
При необходимости задайте поддерживаемую моделью `FINBOT_JUDGE_TEMPERATURE`.
Затем включите **Оценить итерации постоянной моделью после прогона** или
`evaluate_iterations: true` в конфигурации серии. По умолчанию дополнительных
запросов нет. Mock-прогоны не передаются оценщику.

Выбранный для проекта вариант:

```dotenv
FINBOT_JUDGE_KIND=gemini
FINBOT_JUDGE_MODEL=gemini-flash-lite-latest
FINBOT_JUDGE_BASE_URL=https://generativelanguage.googleapis.com/v1beta/models/gemini-flash-lite-latest:generateContent
```

Нативный адаптер Gemini отправляет POST `generateContent` с заголовком
`X-goog-api-key`, значение берёт из `OPENAI_API_KEY`. Для этого адаптера
`FINBOT_JUDGE_API_KEY` не используется. Сохраняются `modelVersion`, исходный
`usageMetadata`, JSON ответа и фактические параметры запроса. В нормализованном
usage выход включает `candidatesTokenCount` и известный `thoughtsTokenCount`;
исходные значения остаются в ответе. Формат запроса соответствует
[документации generateContent](https://ai.google.dev/api/generate-content?hl=en).
Алиас `latest` не закрепляет конкретные веса: для сравнения можно фильтровать
по сохранённой версии модели оценщика.

Если обычный `curl` работает через настроенный `HTTPS_PROXY`, включите для
Gemini `FINBOT_JUDGE_USE_ENV_PROXY=true`. Адаптер будет использовать прокси
из окружения процесса, сохраняя hostname endpoint для CONNECT. По умолчанию
используется прямое подключение с проверкой и фиксацией DNS-адреса. Для Docker
переменные прокси нужно передать в окружение контейнера; переменных только
в терминале хоста недостаточно. Режим прокси также фиксируется в политике оценки.

Worker оценивает сохранённые трассы после завершения основного запуска.
Оценщик получает только данные, доступные до конца конкретной итерации,
включая результаты её инструментов; поздние итерации и исход сценария ему не
передаются. Ответ не поступает исследуемым агентам. Оркестратор тоже сохраняет
собственные итерации, отдельно от дочерних исполнений.

Модель, endpoint, протокол, параметры, промпт и версия методики фиксируются при
создании запуска. Если настройки оценщика изменились, старые задания оценки
не выполняются другой моделью. Сохранены исходный ответ оценщика, запрошенная
и возвращённая модель, usage, длительность и ошибки. Его usage не смешивается
с метриками и стоимостью исследуемой модели.

`Δconf = c₁ − cₖ` вычисляется отдельно для каждого исполнения агента, по
внешним оценкам первой и последней итерации; отрицательное значение означает
рост уверенности. Сохраняются весь профиль и соседние разности. Для одного
шага или отсутствующих/незавершённых оценок Δconf остаётся неизвестной.
Сам оценщик может вернуть `null`, если вывод нельзя оценить. Слишком большой
контекст не обрезается молча: оценка получает `skipped`. Сбой оценщика не
меняет исход основного прогона. Платные запросы после ошибки или прерывания
автоматически не повторяются; в деталях есть отдельная кнопка повтора только
незавершённых оценок. Уже успешные оценки сохраняются.

Отдельный раздел [«Аналитика»](analytics.md) доступен по `/vendor/analytics`:
карта типов по моделям, матрицы ошибок, частоты, температурные и seed-срезы,
профили уверенности и производные описательные признаки. Автоматические,
ручные и судейские метки разделены. Причинный RR, интервенционная EAR и
статистические проверки гипотез требуют отдельного исследовательского анализа.

## Дополнительные таблицы PostgreSQL

После обновления выполните повторно:

```bash
python -m finbot.experiments.archive_cli init
python -m finbot.experiments.archive_cli check
python -m finbot.experiments.archive_cli check --write-probe
```

`check --write-probe` вставляет связанный тестовый набор, читает его обратно
и обязательно откатывает транзакцию. Тестовые строки в архиве не остаются.

Добавочная миграция `sql/results_v2.sql` создаёт:

| Таблица | Содержание |
| --- | --- |
| `cm_series_configs` | Сохранённые манифесты и время создания |
| `cm_series` | Манифест серии, развёрнутый план, время и статус исполнения |
| `cm_series_runs` | Связь серии с архивными запусками |
| `cm_case_observations` | Раздельные слои измерений и профили уверенности |
| `cm_agent_iterations` | Итерации с привязкой к конкретному исполнению агента |
| `cm_iteration_evaluations` | Ответы внешнего оценщика и его уверенность |

Базовые таблицы и представления сохраняют прежний формат. Если они принадлежат
другому пользователю, `init` проверяет базовую схему и создаёт только расширение;
нужны права `CREATE` в `public` и `REFERENCES` на базовые таблицы. Для записи
нужны права DML на базовые таблицы и новые таблицы расширения. Доступ другим
пользователям к новым таблицам настраивается владельцем БД.

Манифесты и состояния серий отправляются через устойчивую очередь синхронизации,
не дожидаясь завершения всей серии. Итерации и оценки архивируются вместе с
результатом запуска; появление оценки повторно ставит результат на отправку.
Ошибка PostgreSQL не вызывает повтор исследуемой модели или оценщика.

Пример чтения измерений:

```sql
SELECT r.model, r.config, c.scenario_id, c.repeat_index,
       i.agent_name, i.source_agent_run_id, i.iteration_index,
       i.vanilla_confidence, i.lexical_confidence,
       e.status AS evaluation_status, e.confidence AS judge_confidence,
       e.error_present, e.assessment
FROM public.cm_runs r
JOIN public.cm_cases c ON c.run_id = r.id
JOIN public.cm_agent_iterations i ON i.case_id = c.id
LEFT JOIN public.cm_iteration_evaluations e ON e.iteration_id = i.id
WHERE NOT r.is_demo
ORDER BY r.started_at, c.scenario_id, c.repeat_index, i.source_agent_run_id, i.iteration_index;
```
